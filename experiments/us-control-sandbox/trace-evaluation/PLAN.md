# Trace-quality stress evaluation 0.1

2 October 2026. Commit this plan before constructing its packet set. This is an author-exposed technical stress evaluation of existing procedures 0.1. It is not a preregistration, independent holdout, TAE/HIT assessment or study of human readers.

## Fixed comparison and selection

Compare the existing checklist and full trace without modifying them after observing results. Both receive identical envelopes. They share validation, extraction and decision rules; label agreement and greater trace coverage are expected by design. This exercise quantifies their explanation differences and exposes implementation defects. It cannot establish independent superiority or justify adoption by itself.

Construct twelve valid packets in four purposive strata of three: combined evidence gaps; mixed request identities; conflicting acknowledgments; and determinate controls. Add three excluded intake challenges: digest mismatch, unsupported scope and an inconsistent effect count. These are newly authored combinations and variants of already exposed mechanisms, not twelve independent case families or new executed system events. The controls deliberately overlap prior examples.

Each packet remains a single authored terminal-record unit with one of the three existing objectives. No person, real organization, protected data, external model or service is involved. There is no separate actual-execution answer for these constructed records; do not claim the packet describes an independently verified outcome.

## Key and information boundary

Write a separate reference key before running either procedure. For each valid unit, record the expected evidence label, three check states (true/false/null), allowed locators for each check, objective, scope, packet hash, rationale and strata. For each excluded unit, record why intake must reject it. Key authorship is Codex-assisted under the user's research direction; independent review is absent.

The procedure phase reads inputs only and saves both outputs, rejections and input hashes before the audit phase opens the key. This is code-path separation, not an access-control or blinding claim: the author has seen both and the repository will publish both. Preserve exact source and key bytes with the output. Never use future evaluator outputs to revise this key silently.

## Measures fixed before construction

An independent material blocker is a reference check whose state is false. A null dependent check is not another observed blocker. Missing downstream evidence and a dependent unassessable fit check therefore contribute one blocker, not two.

Report per unit, per procedure and pooled counts:

- Omitted material blockers: reference-false checks absent from the output or not correctly asserted with an allowed locator, divided by all reference-false checks.
- Incorrect check assertions: reported check states that differ from the reference, including turning null into false, divided by reported check entries.
- Locator errors: reported checks without a nonempty, allowed locator list, or a wrong determinate outcome locator, divided by all reported check entries plus any determinate outcome locator.
- Dependent blocker labels: reference-null check names listed in the trace's blocker list. Report this separately as a presentation observation, not an independent fault or automatic semantic error.
- Output burden: total UTF-8 bytes of compact, sorted-key JSON and number of check entries; report paired differences over the same twelve units. Bytes do not measure reading time, cognitive burden or usefulness.

Unknown or duplicated check names and missing required result fields invalidate the audit rather than improving its denominator. A bad label is also evaluated by the separate technical-evidence label measures; zero denominators remain null. Narrative meaning beyond the fixed mechanical assertions is not independently reviewed. The audit must not call the procedures or their fact extractor to construct expected answers.

The checklist is allowed to stop after its first unresolved condition. Count its omitted subsequent blockers to describe that design tradeoff, not to allege nonconformance. Do not combine metrics into a score or invent a cost/benefit threshold after seeing byte counts. More text is not automatically better evidence.

## Execution, failure and reporting

Before procedure execution, commit inputs, key, audit code and runner. Record the plan commit and the pre-run implementation commit. Keep all fifteen units in the intake accounting. A valid unit rejected by a procedure or an invalid unit accepted is an operational failure and prevents a clean comparison; retain outputs and report the failure. No post-response exclusion or replacement is permitted.

Complete response capture before auditing. If the runner or audit fails, retain available inputs and failure details in a new attempt folder; do not overwrite it. No procedure revision is permitted within this attempt. A later fix requires a new version/attempt with the exposed cases classified as development data.

Publish inputs, key, original outputs, source snapshots, hashes, results and limitations. Report engineering checks separately from observed comparison counts. No inferential statistics, field prevalence, independent validity, superiority or human-assessment benefit is claimed. The research result may be that extra trace content has an unproven benefit despite additional size.
